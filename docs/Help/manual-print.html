Using and maintaining translations

VCL2FMXConverter v7.0 Atlas. Updated October 15, 2026.

This guide explains how to use the 35 included languages, correct a translation, add a language, and install the resulting language pack. It also explains which text is translated and how translated Help differs from the converter interface.

PDF and editable DOCX editions are included in docs/Help/guides. Open these files from the documentation folder, or use the Translation Guide links on the downloads page.

Choosing a language and opening Help

Start Atlas and use the Language selector in the header. Each choice includes its native name and locale code, such as fr-FR. Select a language to update the interface. The selection is saved for the next launch. On first use, Atlas attempts to use a supported system language; English is the fallback.

The 35 bundled interface packs work offline. Select English at any time to return to the source wording. Language selection changes presentation; it does not change the conversion rules or translate the application you are converting.

  1. Select the desired language in Atlas.
  2. Click Help. The installed manual opens in your browser with that language requested.
  3. Allow the online translation service time to load. Keep Atlas running while navigating Help.
  4. After changing the converter language, click Help again to open it with the new selection. An already open Help tab does not automatically follow later changes in Atlas.

English Help remains readable offline. Opening docs/Help/index.html directly as a file also provides English Help. Use the Help button for automatic translation. Downloaded PDF and DOCX guides are English documents and are not translated by the Help widget.

Understanding what is translated

The interface pack supplies captions, instructions, built-in messages, reference-table explanations and other display text. Arabic, Persian, Hebrew, Pashto and Urdu also use right-to-left text presentation. Delphi identifiers, component names, paths, code examples and source evidence retain their original spelling where protected by the application.

The live conversion log is translated for display. Saved HTML and text reports use the language selected when the conversion starts. Selecting another language afterward does not rewrite reports already saved. JSON reports retain canonical English text and the stable report schema so tools can process them consistently.

Generated Pascal, FMX forms and project files are conversion output, not natural-language translations. A language pack changes displayed explanations; a mapping pack changes conversion mappings. Custom mapping-pack notes and external exception messages may remain in their original language.

Help uses a separate online translation service. Atlas serves the installed English pages through a local browser connection and passes the selected language to the translation widget. Help text is processed by that service. The converter's offline interface translation does not require that connection.

The included packs are machine translations and have not been reviewed by native speakers. Structural validation checks such things as placeholders and pack identity; it does not establish linguistic accuracy. Correcting an interface pack does not correct an online Help translation. Permanent Help wording changes belong in the English Help source; translation-service wording is a separate concern.

Preparing Translation Studio

Download the Delphi App Translation Studio (https://delphitranslate.github.io/) and its manuals and guides. Use its Maintenance Studio for the already integrated Atlas project. Atlas already contains its language manager and selector; ordinary translation maintenance does not require repeating component integration or rebuilding the converter.

Use a separate working copy of the matching V7 complete source package. It must contain VCL2FMXConverter.dproj, the source files, Localization/Development, Localization/Languages and the supplied translation metadata. Open the converter project, not the project you intend to convert. The executable-only package is sufficient to run Atlas, but is not the complete Studio editing workspace.

Development catalogs, named VCL2FMXConverter.<locale>.translation-project.json, contain editable entries, source keys and review information. The smaller <locale>.json runtime packs are what Atlas loads. Keep both kinds of file; a runtime pack is not a replacement for its development catalog.

Back up the working catalogs and installed packs before editing. Keep the original V7 English catalog and existing catalogs together so scanning can recover the project's runtime text contracts.

Manual editing needs no translation-provider account. Studio's Translate Automatically command uses its configured provider settings. Follow the Studio guide for the provider you select; those settings are separate from Atlas Help's online widget. Review exactly which text a provider operation will send.

Correcting an existing translation

  1. Open Maintenance Studio. Under Project, open VCL2FMXConverter.dproj from the matching source workspace.
  2. Under Translate, use Open... to open the existing development catalog for the language you want to correct. Check its target locale and native language name.
  3. Choose Scan Project to compare the catalog with the saved forms and source. Review entries marked new, changed or obsolete. Do not discard runtime entries merely because they are not visible form captions.
  4. Select the affected entry. Read its source text and context, edit Translated text, and choose Apply Translation. Use Save to save the catalog.
  5. Use Mark Reviewed only after reviewing the translation's meaning. Approve records a separate final decision. Do not bulk-approve machine output just to clear a status.
  6. Continue with validation, export and installation as described below.

Preserve format placeholders such as %s, %d and indexed variants, deliberate line breaks, HTML structure and protected Delphi identifiers. Translate the surrounding sentence rather than changing keys, component names or metadata.

For work outside Studio, CSV Out and CSV In provide an interchange workflow. Edit only the Translation column, then review the import's conflicts and protected-entry decisions. The development JSON catalog remains the complete record.

Adding another language

  1. Save and close any catalog you are editing. Start a fresh Maintenance Studio session and open the same V7 converter source project.
  2. Run Scan Project to create a fresh catalog from the converter and its supplied workspace metadata. Do not open an existing non-English catalog and simply change its locale; that can retain the old translations and catalog filename.
  3. Under Translate, keep the source language English and choose the new target language. Verify its native name, direction and locale formats.
  4. Choose Save. Check that the resulting development filename contains the new locale and does not overwrite an existing language.
  5. Translate the entries manually, through CSV interchange, or with the Studio's configured automatic provider. Review dynamic messages and reference-table descriptions as well as form captions.
  6. Validate, export the new runtime pack and install it beside the existing packs. Restart Atlas and select the new language.

The filename and pack metadata must describe the same locale. For example, a pack for locale xx-YY is named xx-YY.json; this is a placeholder, not a real language to select. Renaming another language's file does not create a translation.

A supported, valid additional interface pack is discovered at startup without recompiling Atlas. Additional Help languages are not automatic: the Help script has an explicit supported-language list. A maintainer must confirm service support, language-code mapping and right-to-left handling before extending that list. Otherwise Help falls back to English for an unsupported language.

Keeping terminology consistent

Use Studio's Glossary page to maintain preferred wording for a particular project and language. A glossary is useful when the same concept appears in a button, status summary, report and reference description.

  1. Open the V7 converter project and select the glossary's target language.
  2. Enter the Source term and Preferred translation. Add a semantic concept or explanatory note when it helps distinguish meanings.
  3. Choose Add / Update Term, then Save Glossary. Mark terminology approved only when that wording has actually been accepted.
  4. Review the affected catalog entries. Use Apply and Deploy when you intend Studio to apply the terms and regenerate/deploy the corresponding pack to its detected application outputs. Confirm the reported destinations.
  5. If you export or install manually, follow the next section. Restart the particular Atlas copy you are testing.

Saving a glossary alone stores the terminology; it does not update an already running converter. Keep the glossary with the source workspace so later translation work uses the same vocabulary.

Check context rather than applying a literal substitution everywhere. For example, a conversion mapping and a language translation are different operations. Preserve product names and Delphi API names. Keep rule-family names identical in their switches and summaries.

Studio glossary changes affect exported interface/report text. They do not configure the online Help translation service. If a Help term needs clarification, improve the English explanation and check the translated page separately.

Exporting installing and testing a pack

  1. Save source files and the development catalog. Run a fresh Scan Project if source files were saved after the last scan.
  2. Under Validation, choose Run Validation. Correct blocking errors and inspect warnings. Review status and structural validity are separate checks.
  3. Under Export, choose Export Runtime Pack. Studio reports the output path. Keep any accepted layout settings associated with the export; replacing them with another language's geometry can cause clipping.
  4. Close the Atlas copy you are updating. Back up its existing pack outside its language folder, then copy the exported <locale>.json into Localization/Languages beside that executable. Do not put development catalogs or backup JSON files in this runtime folder.
  5. Keep en-US.json installed. Restart Atlas, select the language and check the result. Ordinary text-pack updates do not require recompiling the executable.

Test all seven pages, narrow and maximized windows, the display scaling you use, scrolling to the last paragraph, and switching back to English. Check longer captions, rule summaries, right-to-left text, live messages and reference-table notes.

Run a small sample conversion in a dedicated output folder. Inspect its newly generated HTML and text reports, and open Help from Atlas. Test Help separately because its translations do not come from the interface pack.

To undo an update, close Atlas and restore the backed-up pack, then restart. Keep customized catalogs and exported packs separately before replacing Atlas with a later version; an application update may replace bundled files.

Resolving problems and reporting corrections

A language is absent. Confirm you updated the folder beside the executable you actually launched, that the file is a runtime pack rather than a development catalog, and that its locale, application identity and framework are valid. Restart Atlas after adding files. Do not create duplicate packs for the same locale.

Some text remains English. First distinguish protected identifiers and source evidence from user-facing prose. Missing translations can fall back to English. Check the matching catalog entry, validate and export again. Custom mapping notes and external exception messages may require separate attention.

Text is clipped or overlaps. Record the selected locale, affected page, window size and Windows display scaling. Check the wording and accepted layout settings. Do not shorten a translation so much that it changes the instruction's meaning.

Help remains English. Open it from Atlas, keep Atlas running, and check Internet access and browser restrictions on the translation widget. A newly added interface language may need a Help mapping update. English remains available if translation cannot load.

A saved report uses the previous language. Existing reports retain the language captured for that run. Choose the language before starting the next conversion.

To report a correction, email churchesite@gmail.com or use the translation feedback instructions. Include the converter version, locale, screen or Help topic, current wording and proposed wording. Remove private paths and project details from screenshots and reports. An email template opens for review; it sends nothing automatically.

Translation files and maintenance responsibilities

Localization/Languages contains the installed runtime packs. They identify applicationId as VCL2FMXConverter, use the FireMonkey framework, and retain en-US as the source language. The selector discovers compatible packs; the advertised count of 35 describes the bundled set, not a hard-coded interface limit.

Localization/Development contains the editable catalogs. Localization/Layout records language layout proposals, while runtime packs contain accepted layout rules used by the application. Preserve these files and the project terminology metadata when maintaining translations.

The designer-owned language manager applies the selected pack to form controls, dynamic text and embedded reference content. It preserves control state, saves the user's selection, and falls back to source-language behavior when a pack is unavailable. Developers should keep control properties editable in the Form Designer.

The installed Help lives under docs/Help. Its editable Help Doc Creator project is docs/guides/VCL2FMX User Help.hdc.json in the source workspace. Keep that project, exported topics, navigation/search indexes and printable manual synchronized when changing English Help.

docs/Help/assets/help-translation.js maps converter locale codes to the online service. Maintainers adding Help support must check the supported list, aliases and direction handling, then run the Help translation checks. Adding a JSON interface pack alone does not alter this script or the website's language list.

For source maintenance, the existing language, form, report and Help checks under tools help verify coverage and behavior. These checks complement native-speaker review and visual testing; they do not replace either.

1. Purpose and Audience

The VCL2FMXConverter exists to automate the majority of the engineering work involved in moving a Delphi application from standard VCL to FMX. It is intended to reduce repetitive migration labor, surface the most important conversion risks early, and leave the user with an FMX project that can be compiled, tested, and polished in Delphi.

This manual is written for people who will actually operate the converter. That includes developers converting their own applications, technical staff helping with migration efforts, project owners supervising conversion work, and maintainers who need to understand how to rerun the tool safely and interpret its output.

  1. Use this guide when you need to run the converter, interpret its output, and validate the converted FMX project.
  2. Use the engineering guide when you need to understand the converter internals
  3. Use both guides together when a conversion is being actively refined and stabilized.

2. What the Converter Is, and What It Is Not

Converter BehaviorWhat It Means in Practice
Automates most of the migration workThe converter handles the majority of syntax, form, mapping, and startup translation work automatically.
Works as a migration system, not a blind text replacerIt uses parsing, mapping, and rewrite logic rather than relying only on global text substitution.
Aims for buildable and reviewable outputThe goal is not merely changed text; the goal is a project that can be opened, built, and exercised in Delphi.
Leaves a small review tailA converted application can still need font, layout, or minor behavioral review after the automated pass.
Does not replace software testingA successful conversion still needs compile, runtime, and user validation to confirm the result is correct.

A useful way to think about the converter is this: it is a serious productivity accelerator, not a promise that every converted application is instantly production-ready without verification. In practice, it can bring the vast majority of a migration under control and make the remaining issues understandable.

The current generic baseline is broader than the earlier public-review drafts. It now includes safer FMX form emission, broader standard-control coverage for items such as TMaskEdit, TStaticText, TFlowPanel, TGridPanel, TCheckListBox, TRichEdit, TDrawGrid, TDBCtrlGrid, TFileSaveDialog, and TLinkLabel, and direct numeric-control handling for TNumberBox and converted TSpinBox workflows. It also adds generated compatibility paths for TRadioGroup and TFontDialog, along with more honest blocking-issue reporting when the converter knows the output is not yet trustworthy.

The live Component Map, Property Map, and Event Map pages are now backed by the same current mapper knowledge used during conversion. That makes them the best quick-reference view of what the current v7.0 Atlas build knows about standard component, property, and event coverage. Version 7.0 Atlas also supports optional JSON mapping packs that make third-party component handling visible and auditable before a conversion run.

2.1 Mapping Packs: Optional Third-Party Component Support

A mapping pack is an optional JSON file that gives the converter explicit knowledge about component libraries outside standard VCL. The converter still performs the normal VCL-to-FMX migration work on its own but mapping packs add a separate, visible layer for third-party controls so those decisions can be reviewed instead of hidden inside converter code.

Use mapping packs when a project contains controls from libraries such as DevExpress, TMS, Raize/Konopka, JVCL, EhLib, InfoPower, TeeChart, FastReport, Devart, IntraWeb, UniGUI, or VirtualTreeView. The pack can identify the original VCL class, choose a safe action, map simple properties and events, and explain anything that still requires manual review. This version includes mapping packs for the stated third-party vendors, but while these are included, they do not represent full conversions of the components but rather as much as possible at this point in Delphi FMX.

A mapping pack does not install a vendor product, prove that a commercial component has a full FMX equivalent, or remove the need to test the converted application. Its purpose is to make third-party handling predictable: simple controls may convert, approximate controls may convert with warnings, complex controls may be report-only, and nonvisual or cross-platform items may be preserved when that is the safest choice. Again, they do not represent full conversions of the components but rather as much as possible at this point.

Mapping-pack actions

ActionWhat it means for the user
convertThe converter can generate the target FMX component with reasonable confidence.
partialThe converter can generate an approximate FMX component, but the report must describe the limitations.
manual_reviewThe converter should report the component and avoid unsafe automatic conversion.
detect_onlyThe converter identifies the component or vendor but does not generate a replacement.
preserveThe converter may keep the original class/reference when preservation is safer or explicitly intended.

For normal operation, keep the mapping_packs folder beside VCL2FMXConverter.exe, in whatever folder you install it.

For example if the converter structure is similar to: C:\converter\VCL2FMXConverter.exe

then the mapping packs would be in: C:\converter\mapping_packs\

The packs act as companion files in unison with the converter executable. After a run, review the generated report and their associated report sections for loaded packs, converted third-party components, partial conversions, detect-only findings, preserved components, unknown third-party-looking components, and manual-review reasons.

How to read mapping-pack results

The generated report is a detailed audit trail. If a pack converts a component, the report should say which pack was used and what confidence level was declared. If a pack only detects a component, the report should explain why no FMX replacement was generated.

3. System Requirements and Workspace Preparation

  1. A Windows development environment with Delphi installed and working.
  1. Access to the original VCL source code and form files.
  1. A separate target directory for generated FMX output.
  1. Sufficient disk space for source, output, reports, and milestone backups.
  1. A backup strategy before major converter runs or large rule changes.

A clean folder layout is strongly recommended. Keep the converter source, the original VCL project, and the converted FMX output in separate locations. This prevents stale output files from being mistaken for current results and makes it much easier to compare source and target artifacts during troubleshooting.

4. Building and Launching the Converter

  1. Open the VCL2FMXConverter project in Delphi.
  1. Build the converter and confirm the build completes cleanly.
  1. Run the converter application.

Verify that the tabbed workspace opens and that Dashboard, Project Scan, Component Map, Property Map, Event Map, Conversion Output, and Rules are available.

If the converter itself does not build, stop there and resolve that issue before attempting any project migration. The converter must be treated like any other software tool: it needs a healthy build before its output can be trusted.

7. Preparing a Source Project for Best Results

Some preparation work in the source project can make the converter easier to use and the output easier to validate. This is not always required, but it is often helpful.

  1. Know which folder is the real source root and which files are truly active in the project.
  1. Be aware of duplicated unit names or old backup copies inside the source tree.
  1. Understand any database, media, or file-path dependencies that the converted application will need at runtime.
  1. Keep note of major workflows that must be validated after conversion, such as startup, scheduling, playback, database edits, dialogs, and reporting.
  1. If possible, have the original VCL application available for side-by-side behavior comparison.

The converter can do a great deal, but it is still easier to use when the operator knows which source files matter and which business workflows are critical.

8. Running a Conversion

  1. Enter or browse to the source folder.
  1. Enter or browse to the target folder. A convenience folder name is provided if you wish to use it.
  1. Choose PAS only, DFM only, or both.
  1. Set the include-subfolders option and the four rule toggles as needed.
  1. Review the specialized rule choices if your workflow needs a focused retest.
  1. Click Convert and allow the process to complete.

Read the log before opening the output in Delphi. When the HTML report exists, use Open Report or Print Report directly from the converter, and use Open Output Folder when you need the generated files immediately.

For full project migrations, the normal choice is to convert both PAS and DFM files recursively into a clean output folder. Targeted runs are useful only when you already know that a specific phase is the thing under review.

During the same run, the generator can inventory real support files in the source root and in existing build-output folders. That makes the report more trustworthy because helper executables, DLLs, library files, sound-font files, and similar runtime companions are reported from real locations instead of being guessed from quoted Pascal strings.

9. Reading the Log and the Conversion Report

Every conversion run should be reviewed through two channels: the live log in the converter UI and the generated report files in the output folder. When the HTML report exists, the Open Report and Print Report buttons use it first. These are not optional extras; they are part of the operating workflow.

Information SourceWhat It Tells YouHow to Use It

v7.0 Atlas report totals: Total issues means warnings, manual-review items, and errors. Informational notices and dry-run notices are shown separately. Dry-run notices are not counted as conversion issues.

Manual review groups: Click the > arrow on each manual-review item to view affected locations and recommended fixes.

Pay special attention to the final run status. The current v7.0 Atlas report flow distinguishes Blocking issues present, Manual review required, and Clean conversion. The generated report now calls out a recommended next step, Distinct files needing attention, and files with conversion errors. Treat blocking issues as stop conditions even if files were generated. Informational messages about external project assets are different: they warn that companion files may still need manual copying or relocation before runtime testing. Mapping-pack runs additionally report loaded packs, third-party conversions, partial conversions, detect-only findings, preserved components, and unknown third-party-looking classes.

The current report also distinguishes between support files that were actually staged into the FMX output directory and support files that were only found in the source root or beside an existing built executable. Read those companion-file notes carefully, because staging a helper file into the output tree is not the same thing as confirming it will deploy beside the final built executable.

If the report and the compiler disagree, the compiler wins. If Code Insight and the real compiler disagree, the compiler wins again. The memo log and report are aids, not replacements for build and run validation.

Saved HTML and text reports use the language selected when conversion starts; later language changes do not rewrite them. JSON reports remain canonical English. For details, see Using and maintaining translations.

Conversion reportText summary of the run.Keep it for diagnostics and engineering review.
Milestone backupsSnapshots of converter state or other preserved artifacts.Store separately so they do not pollute source or output folders.

Project files now include a more complete FMX shell, and the generator attempts to carry along common companion assets such as .res, .ico, .manifest, and safe local project references. If the source project points at an absolute external asset outside the source tree, you should expect to verify or copy that file manually before runtime testing.

The output folder may now also contain staged runtime companions such as helper executables, DLLs, library files, or sound-font style support files. The generator adds them when it finds real candidates in the source root or in existing build-output folders such as Win32, Win64, Debug, Release, or deploy. Those files are copied to make review easier, but you still need to verify the final deployment location expected by the generated app.

A clean output folder is one of the most important habits in using the converter. Stale generated units and forms can create false problems, hide real changes, and lead Delphi to load the wrong copy of a file.

11. Opening the Converted Project in Delphi

  1. Open the generated project in Delphi.
  1. Let Delphi load the forms and watch for form-reader errors first.
  1. Build the project and capture the real compiler results.
  1. Fix structural problems before pursuing visual polish.
  1. Rebuild and rerun after each significant converter improvement.

The converter now strips or remaps several common VCL-only form properties before Delphi sees the FMX output, so some earlier reader failures no longer appear. Even so, form-reader errors still deserve first priority because they block every later stage of validation.

The first successful load of the project is a major milestone, but it is not the end of validation. A project can open and still fail at compile time, or compile and still fail at runtime. Treat these as separate checkpoints.

12. Validating the Converted Application

Validation LayerGoalTypical Questions
StructuralCan Delphi read the generated forms and units?Are there reader errors, malformed collections, or invalid properties?
Compile-timeDoes the project build on the first pass?Are units missing, events wrong, or symbols unresolved?
RuntimeDoes the application start and execute real workflows?Do timers, media, data, dialogs, and navigation work?
VisualDoes the application look acceptable and remain usable?Are fonts, labels, colors, and layouts readable and sensible?

Validation should now explicitly cover the newer generic support surface. That includes numeric entry controls, radio-group style selections, font-picking workflows, scrollable long-message dialogs, and any wave-audio paths that depend on Winapi.MMSystem or waveOut APIs.

Real validation means exercising the actual workflows that matter to the application: data entry, startup, scheduling, media playback, dialogs, and reporting. A converted app is only as good as the workflows it can successfully perform.

13. Test startup and shutdown behavior.

  1. Test any timers or schedules if the original app depended on them.
  2. Test data-aware screens and save/cancel workflows.
  3. Test media or file operations where applicable.
  4. Test secondary forms, help, menus, and common user actions.
  5. Test numeric entry controls such as TNumberBox and converted TSpinBox screens.
  6. Test TRadioGroup and TFontDialog workflows if the original application used them.
  7. Test wave-audio or WinMM paths where the source project uses MMSystem or waveOut APIs.
  8. If the application launches, check operation of help files, external documents, URLs, or utilities.
  9. If a form uses shared datasets, shared datasources, shared navigators, or shared combo controls, close and reopen the form and verify the shared object still behaves correctly afterward.

14. Troubleshooting and Recovery Procedures

SymptomLikely CauseRecommended Response
Form reader errorAn unsupported VCL property or malformed FMX output was emitted.Fix the converter rule, regenerate into a clean output folder, and retest.
Compiler errors after regenerationA converter rule is missing or incomplete.Treat the compiler message as the next engineering target and improve the converter globally.
Runtime access violationA startup, event, media, drawing, or binding mismatch remains.Trace the workflow, isolate the phase, and improve the converter behavior globally.
Visual mismatch onlyThe app is basically working but presentation differs.Defer deep visual polishing until structural and runtime behavior are stable.
Code Insight disagreementThe IDE parser is stale or confused.Trust the real compiler and reopen files or restart the IDE if needed.
Conversion completed with blocking issuesA real unsupported component or blocking rule gap was detected.Stop there, read the report, and improve the converter globally before trusting the output.
External project asset reference not copiedThe project shell references a file outside the source tree or in an unresolved path.Copy or relocate the asset manually, then decide whether the generator needs a new generic asset-copy rule.

If a run goes badly, do not try to repair everything at once. The fastest route is usually to identify the highest-severity problem, improve the converter globally, regenerate clean output, and retest.

16. Operational Best Practices

  1. Always keep the source project, output project, and converter workspace separate.
  1. Use clean output folders for serious test cycles.
  1. Back up milestone converter states before risky changes. Backups are extremely important to save accomplished work.
  1. Keep zipped milestone backups out of the live converter workspace so later workspace backups do not recurse and grow uncontrollably. Make sure they are off the development computer in another location, like a cloud service like DropBox, Google Drive, etc.
  1. Treat real compiler output as the authority over IDE-only hints or stale parse errors.
  1. Record what was fixed globally so later projects benefit immediately.
  2. Do not burn time on tiny visual tweaks until the application builds and runs

v7.0 Atlas - September 9, 2026: The suite now contains 227 executable expectations and the latest verification run passed 227 of 227 contracts. The current release also includes standard VCL classification for TBitBtn and TTrayIcon, with conservative FMX substitution or manual-review guidance where appropriate.

Version 7.0 Atlas adds an executable conversion-contract system. A contract is a small Delphi test case paired with an expectation file. The expectation records the required output, report behavior, uses-clause result, and validation rules for one known converter behavior.

The contract runner is the engineering test utility that finds each expectation file, runs the converter against the matching sample input, and fails if the generated result differs from the expected result. It is not runtime data for normal user conversions.
